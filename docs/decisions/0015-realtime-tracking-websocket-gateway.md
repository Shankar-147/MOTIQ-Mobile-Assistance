# 0015 — Real-Time Tracking: WebSocket Gateway, Presence, and location_pings

**Status:** Confirmed (WebSocket gateway with Redis-adapter scaling, TimescaleDB hypertable for raw pings); **Provisional** (grace-period duration, throttle interval, single-instance-only throttle state, no downsampling)
**Bible chapter to reconcile with:** Ch40 (Time-Series Data Architecture), Ch54 (Real-Time Tracking Service Design), Ch75 (Real-Time Architecture Overview), Ch76 (Presence & Connection State Management), Ch77 (Live Location Streaming Pipeline)

## Context

Ch75 requires a NestJS WebSocket gateway with horizontal scaling via a Redis adapter — named explicitly as closing a V0 gap ("the original diagram showed WebSocket support with no scaling story"). Ch76 requires a provider online/offline/busy state machine with heartbeat and reconnection-storm mitigation. Ch77 requires a mobile→gateway→subscriber pipeline with throttling/batching and multi-subscriber fan-out. Ch40 requires a TimescaleDB hypertable for raw GPS pings with a downsampling policy. Unlike Ch54/Ch75–77, none of which state concrete bullet-point constraints in their condensed form (only purpose statements), Ch40 is specific: hypertable + retention window. Neither PostGIS nor TimescaleDB extension availability has been verified against the local PostgreSQL instance in this environment; Redis has never been confirmed running either.

## Decision

**Gateway**: `TrackingGateway` (namespace `/tracking`) authenticates each WebSocket connection once, at handshake (`handleConnection`), by verifying the same JWT access token HTTP requests use — Passport's `AuthGuard('jwt')` (ADR 0011) doesn't apply to a Socket.IO handshake, so `ws-auth.util.ts`'s `authenticateSocket()` verifies it directly against the same `JwtService`/secret. An invalid or missing token disconnects the socket immediately; there is no per-message re-authentication (a long-lived, already-authenticated connection re-checking on every message adds cost with no additional safety).

**Fan-out** (Ch77) is room-based: a provider's accepted location update broadcasts only to the Socket.IO room `service-request:{id}`, which customers/Admin/Support join via `subscribe:request` (with the same ownership check as `RequestController.findOne()` — a Customer may only subscribe to their own request). This is real multi-subscriber fan-out (any number of sockets can join the same room), not a single point-to-point channel.

**Throttling** (Ch77): `shouldAcceptLocationUpdate()` (pure, tested) rejects updates arriving faster than `LOCATION_UPDATE_MIN_INTERVAL_MS` (default 3s) per provider, tracked in an in-process `Map`. **Batching is not implemented** — each accepted update is a single `LocationPing` insert; buffering multiple pings into one write was judged premature optimization at zero traffic (see Consequences).

**Presence/heartbeat** (Ch76): a `presence:heartbeat` message bumps `ProviderProfile.lastSeenAt` without requiring a location. **Reconnection-storm mitigation**: `handleDisconnect` does not mark a provider `OFFLINE` immediately — it schedules a 30-second grace-period timer (`PRESENCE_OFFLINE_GRACE_MS`); a genuine reconnect within that window (`handleConnection` for the same `providerProfileId`) cancels the pending timer. The policy's boundary logic is captured as a pure, tested function (`presence-grace.util.ts`) even though the gateway itself uses `setTimeout` (the natural implementation for "fire once after N ms") rather than polling that function directly.

**ETA recomputation** (Ch54, and — directly — ADR 0007's binding fallback obligation): every accepted location update from a provider currently holding an accepted `Assignment` recomputes distance-to-pickup (PostGIS `ST_Distance`, `ProviderService.getDistanceToServiceRequestPickup`) and an ETA range (`estimateEta()`, ±30% around a fixed 30 km/h assumption) broadcast alongside the location. This is the first real implementation of the ETA fallback ADR 0007 only promised in Phase 0 — there is still no ML ETA model (Ch85), so this range **is** the whole implementation, not a degraded mode, and it deliberately returns a range rather than a point estimate, per Ch1's "never false precision" rule.

**Horizontal scaling** (Ch75): `RedisIoAdapter` (`common/redis-io.adapter.ts`) attaches `@socket.io/redis-adapter` when `REDIS_URL` is set and reachable; otherwise it logs a warning and the gateway runs single-instance — the same "degrade honestly, never crash" posture as `RazorpayGatewayAdapter` and `NotificationService`. **Not verified against a real Redis instance** in this environment (confirmed via a targeted script: both the unset-`REDIS_URL` and unreachable-`REDIS_URL` paths degrade without throwing, but no actual pub/sub fan-out across instances has been exercised).

**`location_pings`** (Ch40): a `LocationPing` model with a composite `(id, recordedAt)` primary key — not a plain single-column PK — because TimescaleDB requires any unique/primary-key constraint on a hypertable to include the partitioning column. Deliberately **plain `latitude`/`longitude` Floats, not PostGIS geography** — Ch39's binding "PostGIS required" rule is scoped to the nearest-provider query path (`ProviderProfile.currentLocation`); this table is a historical trail, never queried for proximity, so the added complexity of combining hypertables with PostGIS geography columns wasn't justified. Extension enablement and hypertable/retention-policy creation are hand-written SQL (`pre-migration-timescaledb-extension.sql`, `post-migration-timescaledb-hypertable.sql`), the same two-script pattern as PostGIS (ADR 0002) — **TimescaleDB's availability has not been verified** in this environment, a materially bigger unknown than PostGIS (which is a common, often-bundled Postgres extension; TimescaleDB is not).

## Alternatives Considered

- **Per-message WebSocket auth via a NestJS `WsGuard` on every `@SubscribeMessage`.** Rejected — redundant given handshake-time auth on a long-lived connection; adds latency to every message for no real safety gain at this phase's scale.
- **Marking a provider `OFFLINE` immediately on socket disconnect.** Rejected — Ch76 explicitly names reconnection-storm mitigation as a requirement; mobile networks disconnect/reconnect routinely without the provider actually leaving.
- **PostGIS geography for `location_pings` too, for consistency.** Rejected — this table is never used for proximity queries, and combining a PostGIS geography column with a TimescaleDB hypertable (which already complicates the primary key) was judged to add real complexity without a corresponding real need in this phase.
- **A shared/distributed throttle store (Redis) instead of in-process `Map`.** Rejected for this phase — the WS gateway itself is not yet proven to run multi-instance in this environment (see the Redis-adapter caveat above); a per-instance throttle map is consistent with that reality and simpler.

## Consequences

- The in-process throttle `Map` in `TrackingService` is per-instance — if the gateway does eventually run multi-instance behind the Redis adapter, a provider's rapid reconnect to a *different* instance would reset their throttle window. Not a correctness bug (worst case: one extra accepted update), but a known limitation, not silently assumed away.
- No downsampling (continuous aggregates) is implemented for `location_pings` — only raw-data retention (90 days, Ch40's illustrative example). Long-term, lower-resolution history is real future work.
- `apps/mobile` doesn't exist yet (ADR 0008), so this gateway has never been exercised by a real mobile client — only by the DI-graph boot check and the pure-function unit tests. The wire protocol (`location:update`, `subscribe:request`, `presence:heartbeat`) is the first thing a future mobile client implementation needs to match exactly.
