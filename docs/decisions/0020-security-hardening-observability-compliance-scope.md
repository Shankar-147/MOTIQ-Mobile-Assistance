# 0020 — Security Hardening, Observability, Compliance: What Phase 7 Builds and Defers

**Status:** Provisional
**Bible chapters to reconcile with:** Ch92–100 (Volume IX, Security/Trust/Safety), Ch101–117 (Volume X, Infrastructure/DevOps/SRE), Ch126–132 (Volume XII, Legal/Privacy/Compliance)

## Context

Volumes IX, X, and XII together span 33 chapters. Roughly half of them (Ch101–108's cloud/CI/CD/secrets-manager chapters, Ch112–117's alerting/synthetic-monitoring/backup/DR/chaos-engineering chapters) presuppose real deployed infrastructure — a chosen cloud provider (Ch101, itself still open), a running CI/CD pipeline, a monitoring/paging stack. This bootstrap has never had any of that; every prior phase's Reconciliation Notes have said so consistently. Several Volume XII chapters (Ch129 Terms of Service/liability, Ch130 gig-worker classification) are legal-drafting exercises that need real counsel, not fabricated boilerplate from a coding session.

What this phase can responsibly do: build every piece that's genuinely **code**, not infrastructure or legal drafting, and write honest process documents (a threat model, an incident-response procedure, SLO targets) for the rest — the same "real code + explicit deferral" discipline every prior phase has followed.

## Decision — built this phase, as real code

- **Ch95 per-user rate limiting**: `@nestjs/throttler` globally, tracked by JWT subject (decoded, not verified — bucketing only, never a substitute for real auth) when a Bearer token is present, falling back to IP for unauthenticated requests. Tighter per-route limits on OTP request/verify, admin login, and AI Assistant messages. Closes the exact gap `docs/security.md` has flagged as missing since Phase 1.
- **Ch93 MFA**: opt-in TOTP for Admin/Support accounts (`otplib`), a standard RFC 6238 implementation any authenticator app supports. Enrollment is two-step (generate, then confirm with a real code) so `mfaEnabled` never flips true on an unconfirmed secret.
- **Ch94 field-level encryption**: AES-256-GCM (`encryption.util.ts`), applied to `ProviderVerificationDocument.fileUrl` — the most sensitive currently-stored field with no functional need to be plaintext-searchable. **Honest gap**: the master key is a bare `ENCRYPTION_MASTER_KEY` env var, not a real KMS-managed key (Ch94 ultimately wants the latter) — there is no KMS in this environment. `encryptField()`/`decryptField()` throw clearly rather than silently storing plaintext when unconfigured, the same honesty discipline as every unconfigured third-party adapter in this codebase.
- **Ch99 fraud detection**: `gps-spoof.util.ts` flags a physically-implausible speed between a provider's consecutive `location_pings` (Ch99's named "fake job completion" scenario). Advisory only — `LocationPing.flaggedAsSuspicious` is set and logged, never blocks the tracking write path, matching ADR 0007's "additive, never load-bearing" principle extended from AI to fraud heuristics generally.
- **Ch110/111 logging/tracing plumbing**: `correlation-id.middleware.ts` (an `X-Correlation-Id` generated-or-propagated on every request, echoed in the response header) and `pii-redaction.util.ts` (masks phone/email patterns before they reach a log line). **Honest gap**: this is the plumbing and the convention, not a retrofit of every existing `Logger.log()` call site across ~30 files — that's tracked as follow-up work, not silently claimed done.
- **Ch126/131 DPDP Data Principal rights**: `GET /users/me/data-export` and `DELETE /users/me` are real, callable endpoints (Ch126's binding "must be implementable via real endpoints, not just policy language"). Erasure **anonymizes rather than hard-deletes** — this is Ch131's "reconciles Ch42's retention rules with Ch126's erasure rights; resolves soft-delete vs. hard-delete," resolved here: `phone` is replaced with a synthetic unique value, `email`/`passwordHash` cleared, `isActive` set false, `displayName`/`businessName` overwritten, all refresh tokens revoked — but `ServiceRequest`, `Payment`, `Assignment`, `Rating`, and `AuditLog` rows are never deleted, since other parties' accounts and MOTIQ's own financial/audit trail legitimately still reference them. A **deliberate, bounded exception to ADR 0001's module-boundary rule**: `DataRightsService` reads several other modules' Prisma tables directly rather than round-tripping through each module's exported service, because a DPDP export is inherently cross-cutting by definition (every module's data about one person). This is not a precedent for casual boundary violations elsewhere.
- **Ch128 consent**: a new `ConsentRecord` model, versioned, with a real audit trail. `RequestController.create()` and `ProviderController.updateOwnPresence()` (when it carries a location) both gate on `ConsentService.requireConsent(userId, LOCATION_TRACKING)` — real enforcement, not just a policy document. `apps/mobile` was updated in the same phase to call the grant endpoint at the natural moment (right after the OS location-permission prompt succeeds), so the whole system stays consistent rather than shipping a backend gate the existing mobile client would immediately start failing against.

## Decision — process documents, not code

- **Ch92 threat model** (`docs/threat-model.md`): a real STRIDE analysis against MOTIQ's actual built surface as of Phase 6, not a generic template.
- **Ch100 incident response** (`docs/incident-response.md`): a severity taxonomy and first-response procedure grounded in what's actually built (correlation IDs, `AuditLog`, credential rotation paths that exist today).
- **Ch109 SLIs/SLOs** (`docs/slo.md`): proposed targets per safety-relevant journey, explicitly labeled as proposed-not-measured, since there's no load-tested deployment to measure against yet.

## Decision — explicitly deferred, not silently skipped

- **Ch81, Ch82, Ch86–89, most of Ch91** were already deferred in Phase 6 (ADR 0019) for the same no-trained-model reason; unchanged here.
- **Ch101–108** (cloud provider, VPC, containers, environments, CI, CD, feature flags, secrets manager) and **Ch112–117** (alerting, synthetic monitoring, backup/restore, DR runbooks, chaos engineering, cost optimization): no real infrastructure exists for any of these to configure or test against. Building them now would be exactly the "architecture theater" ADR 0019 already named and rejected for Ch88's model registry.
- **Ch96 mobile app security** (certificate pinning, root/jailbreak detection): would need native modules this bootstrap has never built or run through Metro (see ADR 0018's own caveat) — deferred until `apps/mobile` is actually exercised on a device.
- **Ch97 payment security**: already substantively covered by the Razorpay tokenization boundary and no-raw-card-data schema design from Phase 2 (ADR 0014) — nothing new to add without a real PCI audit, which needs a real payment processor relationship this session doesn't have.
- **Ch127 data localization, Ch129 Terms of Service/liability, Ch130 gig-worker classification, Ch132 accessibility compliance audit**: legal/regulatory-drafting chapters. Ch127 is explicitly reconciled with Ch101's cloud-region choice, which doesn't exist yet. Ch129/130 need real legal counsel — fabricating liability terms or employment-classification positions in a coding session would be actively harmful, not just incomplete. Ch132's accessibility work is partially covered in practice (Phase 5's mobile `a11y.ts` constants) but a real compliance audit checklist needs an accessibility specialist's review, not a bootstrap session's self-assessment.

## Alternatives Considered

- **Skip the whole phase until real infrastructure exists.** Rejected — roughly half of what these volumes ask for (rate limiting, MFA, encryption, consent, DPDP endpoints, a fraud heuristic) is genuinely buildable now and makes the product measurably safer today, not just eventually.
- **Build placeholder infra chapters anyway (a fake CI config, a fake DR runbook) to "cover" every chapter number.** Rejected per CLAUDE.md's "no half-finished implementations" and this codebase's consistent pattern (ADR 0019's same reasoning for Ch88) — a runbook for infrastructure that doesn't exist is fiction, not documentation.
- **Hard-delete on erasure instead of anonymizing.** Rejected — would break referential integrity for every `ServiceRequest`/`Payment`/`Rating` another party's account still legitimately references, and would delete MOTIQ's own financial audit trail, which Indian financial-recordkeeping norms (and Ch42's retention rules, per Ch131's own framing) require keeping regardless of the data subject's erasure request.

## Consequences

- Every new security control here (rate limiting, MFA, encryption, GPS-spoof detection, consent gating) is real and enforced, not documentation — but none of them have been exercised against real production load, real attackers, or a real KMS. Treat this phase's security posture as "meaningfully better than Phase 6's, not yet audited."
- `ENCRYPTION_MASTER_KEY` rotation has no real procedure yet (re-encrypting existing rows under a new key needs a migration script that doesn't exist) — tracked in Reconciliation Notes.
- The consent gate is a real behavior change: a mobile client older than this phase's `apps/mobile` update would start receiving 403s on request creation and going online. Both call sites were updated in this same phase specifically to avoid shipping a backend-only half of this feature.
