# MOTIQ — Phased Implementation Roadmap

Companion to `docs/architecture.md`. Phases 0–4 are complete; this is the proposed sequencing for what comes next.

## Phase 0 — Architecture & Bootstrap (complete)

Environment assessment, technology stack, architecture analysis, domain model, repository structure, `CLAUDE.md`, initial config, git setup, and a working (but feature-empty) skeleton: NestJS modular monolith with real module boundaries, a Prisma schema implementing the full domain model, a fully-implemented `ServiceRequest` state machine with tests, a fully-implemented commission-split calculation with tests, a `ServiceArea` CRUD exemplar, and a Next.js Admin Console shell.

## Phase 1 — Identity & Auth (Ch33, Ch50, Ch51) (complete)

OTP-based phone login/registration for Customer/Provider (`POST /auth/otp/request`, `POST /auth/otp/verify`), password login for Admin/Support (`POST /auth/admin/login`), JWT access tokens with opaque DB-backed refresh-token rotation (`POST /auth/refresh`), and guard-based RBAC (`JwtAuthGuard` + `RolesGuard` + `@Roles(...)`) — see `docs/decisions/0011-*.md` for the full design. `RequestController.create()` now derives `customerProfileId` from the authenticated session instead of trusting client input, closing the exact gap this phase existed to close. **Not fully done**: RBAC is role-based only so far — `ServiceArea` cross-city scoping isn't enforced anywhere yet, and only `RequestController`'s read endpoint has a real ownership check. See the Reconciliation Notes below.

## Phase 2 — Core Transaction Flow (Ch52, Ch53, Ch56, Ch57) (complete)

Real Matching (candidate retrieval via `ProviderService.findNearestAvailableProvidersForRequest`, distance-sort dispatch, reassignment on rejection, timeout expiry via an Admin-triggered sweep), the deterministic Pricing Engine (Ch56, ADR 0012), and Payment settlement (ADR 0014) with a real Razorpay adapter behind `PaymentGatewayPort` and mandatory webhook signature verification. Request/Matching/Payment are wired together for real via domain events (`@nestjs/event-emitter`, ADR 0013) rather than direct module imports. Rating submission (Ch58) is also wired end-to-end, guarded and provider-derived from the accepted `Assignment`. This delivers Ch9's MVP scope minus tracking (Phase 3): request creation, matching, payment, rating.

**Not fully done**: no recurring scheduler triggers timeout reassignment (the logic is real, the trigger is manual); broadcast-to-multiple dispatch isn't implemented (single-offer only); the fare's distance input is match-time straight-line distance, not a live route; the Razorpay adapter has never been exercised against a real sandbox (no credentials in this session). See the Reconciliation Notes below.

## Phase 3 — Real-Time Tracking (Ch40, Ch54, Ch75–77) (complete)

A JWT-authenticated WebSocket gateway (`/tracking`, ADR 0015) with room-per-request fan-out, throttled and persisted location updates (`location_pings`, a TimescaleDB hypertable per Ch40), presence/heartbeat with reconnection-storm-mitigating grace periods (Ch76), and Redis-adapter horizontal scaling that degrades to single-instance if Redis isn't available (Ch75). Every accepted location update from a provider on an active job recomputes and broadcasts an ETA range — the first real implementation of ADR 0007's ETA fallback obligation.

**Not fully done**: no batching of location writes (each throttled update is its own insert); no downsampling for `location_pings` (raw-retention only); the throttle state is per-instance, not shared across a multi-instance deployment; neither TimescaleDB nor Redis has been verified against a real instance in this environment; `apps/mobile` doesn't exist yet, so the WebSocket protocol has never been exercised by a real client, only by DI-graph and unit-level checks. See the Reconciliation Notes below.

## Phase 4 — Provider Verification & Trust (Ch58, Ch61, Ch98) (complete)

A guarded verification-status state machine (ADR 0016, same discipline as `ServiceRequest`'s) replaces the plain-field write that existed since Phase 0. KYC document submission (Provider self-service) and review/tier decisions (Admin, Ch61's "provider-verification workflow backend") are separate, explicit actions — reviewing a document never auto-changes a tier. Re-verification cadence with de-listing triggers (`sweepLapsedVerifications()`, the same Admin-triggered manual-sweep pattern as Matching's timeout expiry) is real. `AuditLog` is now actually wired to real write paths (document review, tier changes, lapsed de-listing) for the first time since Phase 0. Trust score (Ch58) — Bayesian-adjusted rating × verification multiplier, deliberately distinct from raw `ratingAverage` — is computed and stored, feeding a Ch84 ranking model that doesn't exist yet.

**Not fully done**: no document-sufficiency automation (by design — Ch98 doesn't specify one); `fileUrl` is an unvalidated client-supplied reference, no real file storage/scanning; commission-rate changes are still not audit-logged (only verification-related writes are); re-verification sweep has no recurring scheduler, same manual-trigger posture as every other "Ch62 not built yet" item. See the Reconciliation Notes below.

## Phase 5 — Notifications, Mobile Apps (Ch32, Ch59, Ch64–74) (complete)

Real multi-channel notification adapters (ADR 0017): Twilio for SMS (including OTP delivery, replacing Phase 1's console-log-only path), FCM's legacy HTTP API for push, both behind Ch32 adapter ports and degrading to a logged fallback when unconfigured — the same pattern established for Razorpay in Phase 2. Per-user notification preferences and quiet hours are real and enforced, with Ch79's CRITICAL tier (SOS, OTP) always bypassing suppression. `NotificationEventListener` fans out `RequestCreated`/`ProviderAssigned`/`PaymentSettled`/`RatingSubmitted` into push notifications the same way Matching/Payment already reacted to each other (ADR 0013).

The Flutter-vs-React-Native question (ADR 0008) is resolved: **React Native via Expo** (ADR 0018), reasoned from `packages/types`' direct TypeScript sharing and this environment having no Flutter SDK installed. `apps/mobile` is now a real Expo/TypeScript app — Customer and Provider experiences as separate navigation stacks in one codebase (Ch65), covering Ch71's request-creation/live-tracking/payment-rating flow and Ch72's job-offer/accept/status flow at equal depth, Ch66's token-refresh-aware API layer, Ch67's offline request-queuing guarantee, Ch68's foreground-only location streaming, Ch69's WebSocket tracking client, Ch70's Android push registration, and Ch73's shared accessibility constants.

**Not fully done**: `apps/mobile` has been type-checked and linted but never run through Metro, opened in Expo Go, or built for a device/simulator — no Expo/Xcode/Android Studio tooling available in this environment (see ADR 0018). iOS push (needs a separate APNs adapter) and true background location tracking (needs `expo-task-manager`) are both unbuilt. The SOS/SMS-fallback requirement (Ch67, Ch55) has nothing to fall back to yet, since no SOS endpoint exists on the backend. No "list Service Areas" or "my pending offer" endpoint exists for mobile clients, so onboarding/offer-recovery both lean on manual IDs or push-notification delivery with no in-app fallback. Twilio/FCM have never been exercised against real credentials. See the Reconciliation Notes below.

## Phase 6 — AI Capabilities (Ch80–91) (complete)

`AiModule` (ADR 0019) is the concrete home for ADR 0007's `AiCapability` port: `classifyIssueCategory()` (Ch83), `rankProviders()` (Ch84), and `assistantReply()` (Ch90) are all real, callable, deterministic-by-default implementations — not machine-learned, since this bootstrap has no historical data to train against, but genuinely functional. `MatchingService.dispatch()` now ranks candidates by a weighted distance+trustScore score before offering, falling back to plain distance-sort (Ch84/Ch35's binding fallback) if ranking throws. The AI Assistant runs Ch90's mandatory emergency-intent pre-filter before any conversational response, tracks and caps cost-per-conversation, and calls a real Anthropic adapter that degrades to a small hardcoded FAQ responder when unconfigured (no API key in this environment). Ch85's ETA prediction was already implemented in Phase 3 and is unchanged.

**Not fully done, and deliberately not faked**: Ch81 (Feature Store), Ch82 (ML Data Pipeline), Ch86 (Demand Forecasting), Ch87 (Training Pipeline), Ch88 (Model Registry), Ch89 (Drift Monitoring), and most of Ch91 (Governance) are all explicitly deferred — none of them have anything real to operate on (no trained model, no historical demand data) in an environment that has never connected to a live database with real traffic. Most importantly: **Ch90's binding requirement to redirect an emergency to the SOS path cannot be fully satisfied, because Ch55 (the SOS path itself) does not exist yet.** The emergency pre-filter still stops the assistant from conversationally engaging with an emergency, but it can only tell the user to contact real emergency services directly, not redirect into an in-app flow that was never built. See ADR 0019 for the full reasoning and the explicit flag on this gap.

## Phase 7 — Security Hardening, Observability, Compliance (Volumes IX, X, XII) (complete)

Real code where real code was possible; honest documents and explicit deferrals everywhere else (ADR 0020). **Security**: per-user rate limiting via JWT-subject tracking (Ch95, closing a gap flagged since Phase 1); opt-in TOTP MFA for Admin/Support (Ch93); AES-256-GCM field-level encryption applied to KYC `fileUrl` (Ch94); a GPS-spoof heuristic flagging physically-implausible provider movement (Ch99, advisory-only). **Observability**: correlation-ID propagation (`X-Correlation-Id`) and a PII-redaction utility for logs (Ch110/111 plumbing). **Compliance**: real `GET /users/me/data-export` and `DELETE /users/me` endpoints (Ch126's binding "real endpoints, not policy language"), erasure resolved as anonymization rather than hard-delete (Ch131); a real, versioned, audited `ConsentRecord` gate on location collection (Ch128), wired into both `apps/api` and `apps/mobile` in the same phase so the system stays consistent. **Documents**: a real threat model (`docs/threat-model.md`), incident-response procedure (`docs/incident-response.md`), and proposed SLO targets (`docs/slo.md`) — grounded in what's actually built, not generic templates.

**Not fully done, and deliberately not faked**: everything presupposing real deployed infrastructure (Ch101–108's cloud/CI/CD/secrets-manager chapters, Ch112–117's alerting/synthetic-monitoring/backup/DR/chaos-engineering chapters) is deferred — there is no cloud provider chosen, no CI pipeline, no monitoring stack for any of it to configure or run against. Legal-drafting chapters (Ch127 data localization, Ch129 Terms of Service/liability, Ch130 gig-worker classification) need real counsel, not a coding session's invented positions. `ENCRYPTION_MASTER_KEY` is a bare env var, not a real KMS key. See ADR 0020 for the full reasoning and the Reconciliation Notes below for the itemized list.

## Phase 8 — Admin & Operations Console UI (Ch137) (complete)

`apps/web` was Phase 0's empty shell until this phase, despite `AdminController` already having real functionality with no UI to drive it. Built as a Next.js App Router BFF (ADR 0022): the browser never holds a token or talks to `apps/api` directly — every page is a Server Component/Server Action reading an `httpOnly` session cookie server-side. Real, working pages: login (with the MFA flow from Phase 7), a dashboard, the verification-review queue (approve/reject KYC documents), a provider browser with tier-change actions (through the same guarded state machine as every other write path), service-area management (create, launch-phase advance, per-area fare/commission config), the audit log, and MFA enrollment/disable for the logged-in admin. Two small backend additions made the console actually useful rather than decorative: `GET /admin/providers` (there was no way to browse providers before) and `GET /admin/audit-log` (the audit trail had no read path).

**Not fully done**: no silent session refresh (ADR 0022 — an admin re-authenticates roughly every 15 minutes); no manual dispatch override (Ch61's other named Admin responsibility, still unbuilt); a production `next build` fails on the auto-generated `/404`/`/500` error pages specifically (a known monorepo/multiple-React-instance edge case) — `next dev` is unaffected and this hasn't been root-caused yet.

## Phase 9 — SOS & Safety Service (Ch55) (complete)

The most safety-critical piece named across the whole Bible, and the last major gap ADR 0007/0019 had been carrying since Phase 0. A real `SosAlert` entity and `SosModule` (ADR 0021): `POST /sos/trigger` (Customer/Provider) creates an alert and fans out a `CRITICAL` push to every Admin/Support user immediately — explicitly exempted from rate limiting (`@SkipThrottle()`) and from the `ConsentService` location-consent gate, both deliberate readings of Ch55's binding "never delay a genuine trigger" constraint. A guarded lifecycle (`TRIGGERED → ACKNOWLEDGED → {RESOLVED, FALSE_ALARM}`) mirrors Ch19/Ch98's state-machine discipline. The AI Assistant's emergency pre-filter (Ch90, previously a dead end) now files a real alert through a one-way `AiModule → SosModule` dependency, preserving ADR 0007's rule that the *primary* trigger path never depends on AI. The Admin Console gained a `/sos` queue with a dashboard banner for active alerts, and `apps/mobile` gained a persistent `SosButton` on the Customer tracking screen and Provider active-job screen.

**Not fully done, and deliberately not faked**: this is an internal escalation to MOTIQ's own team, not a real emergency-dispatch integration — no software here can actually call police/ambulance, and every response explicitly tells the user to contact real emergency services themselves. No SMS-based offline fallback (Ch67's other named requirement — needs native platform integration this phase doesn't build). No trusted-contacts notification. The SOS button isn't on every screen, only the two highest-risk ones. See ADR 0021.

## Phase 10 — Mobile Home/History/Profile & KYC Upload UI (Ch71, Ch72, Ch98) (complete)

The mobile app's golden-path screens (Phase 5) had no home base: a customer landed straight on the request form with no history, profile, or receipt; a provider landed straight on the presence toggle with no job history, no visible tier/trust score, and no way to submit KYC documents in-app (the endpoint existed since Phase 4, the screen never did). This phase adds a real bottom-tab landing surface to both stacks — `@react-navigation/bottom-tabs`, the natural companion to the `@react-navigation/native-stack` already in use — with the one-off flows (CreateRequest, TrackRequest, RateProvider, JobOffer, ActiveJob, KycUpload) staying on the parent native-stack navigator.

**Customer**: Home (greeting + active-request banner + request CTA), History (cursor-paginated past requests), a new RequestDetail screen (vehicle snapshot, description, and — once settled — a real payment receipt via the new `GET /requests/:id/payment`), and Profile (view/edit `displayName`/`preferredLanguage`, log out). `CreateRequestScreen`'s free-text Service Area ID field — a stand-in flagged since Phase 5 — is now a real picker backed by the already-existing-but-unused `GET /service-areas`.

**Provider**: Home (presence toggle, now with a stats card — tier, rating, completed jobs), Jobs (cursor-paginated assignment history, read-only), and Profile (tier/trust score/rating plus the entry point into a new KycUploadScreen — document-type picker, a reference/URL field consistent with ADR 0016's "no real file storage" honesty, and a list of the provider's own submissions with review status).

**Backend additions**: `GET /requests` (customer's own, cursor-paginated), `GET /requests/:id/payment`, `GET /providers/me`, `GET /providers/me/jobs` (cursor-paginated), and a new `CustomerModule` (`GET|PATCH /customers/me`) — the first read/write path onto `CustomerProfile` outside of `RequestService`'s create-time snapshot.

**Not fully done**: `ProviderJobsScreen` is deliberately read-only. Payment/Provider ownership checks on `GET /requests/:id/payment` stay as loose as `GET /requests/:id` already was (Provider/Admin/Support unrestricted) — see the existing Reconciliation Notes row on this. No pull-to-refresh, no offline-cache for these read screens (a failed fetch just shows a loading/empty state).

## Phase 11 — Live-Tracking Map & Visual Redesign (Ch54, Ch71, Ch72) (complete)

`TrackRequestScreen` (Customer) and `ActiveJobScreen` (Provider) previously rendered raw `latitude, longitude` numbers as plain text — flagged as the single biggest mobile UX gap for a roadside-assistance app once Phase 10 filled in the rest of the screen inventory. Both screens are now a real full-screen `react-native-maps` `MapView` (`LiveTrackingMap`, a shared component) with a pickup pin, a moving marker (the provider's live position on the Customer app, the provider's own position on the Provider app), a dashed straight-line connector between them (honest about not being a real route — Ch32's Maps/routing API integration is still unbuilt, ADR 0012), and a recenter button. Floating cards over the map replace the old plain-text status line: a `StatusTimeline` stepper (Requested → Matched → On the way → Arrived → Completed, collapsed from the full `RequestStatus` enum) plus, on the Customer app, a bottom card showing the assigned provider's name/rating/tier (`GET /providers/:id/public`, a new non-sensitive-fields-only endpoint — a customer previously had zero information about who was coming) and the ETA range. A small shared `theme/colors.ts` token file backs both screens so they read as one consistent visual language instead of independently-styled components.

Two real backend gaps got closed along the way, not just UI: `RequestService.findById()` now reads `pickupLocation` back out via the same raw-SQL escape hatch used to write it (Ch71's map needs real coordinates — the column is a PostGIS `Unsupported(...)` type, invisible to Prisma Client by default, and until now nothing ever read it back). And `ActiveJobScreen` no longer hardcodes `PROVIDER_ACCEPTED` as its initial state — it fetches the request's real status on mount (fixing a real correctness bug flagged during Phase 10's build: resuming a backgrounded app mid-job would have shown the wrong step).

**Not fully done, and deliberately not faked**: still no real route/turn-by-turn (Ch32) — the map shows two points and a straight dashed connector, not driving directions. `react-native-maps` is only verified inside Expo Go (this project has never had Xcode/Android Studio to do a native/EAS build, ADR 0018) — Expo Go bundles its own development Google Maps key for Android, so a future standalone build will need a real key configured in `app.json`, not yet done. The provider's own-position marker on `ActiveJobScreen` runs a second, independent `expo-location` watcher purely for map display rather than reading back `locationTracking.ts`'s existing socket-emitting watcher — simpler, at the cost of two active location subscriptions instead of one while a job is active.

## Phase 12 — gluestack-ui Component Library Retrofit (Ch71, Ch72) (complete)

CLAUDE.md was updated to mandate `gluestack-ui` as `apps/mobile`'s primary UI component library — a real, binding convention, not a suggestion, per the project's discipline of following what CLAUDE.md states. Every one of the 17 mobile source files that render UI (all 3 auth screens, all 7 Customer screens, all 6 Provider screens, and the shared `SosButton`) was rewritten from hand-rolled `View`/`Text`/`Pressable`/`TextInput`/`StyleSheet` to `@gluestack-ui/themed` — the stable, production `v1.1.73` line (NativeWind-based `gluestack-ui@5` is still alpha as of this session and hit real `npm ERESOLVE` peer-dependency failures during a first attempt; the CLI's interactive `v3` line couldn't run at all in this non-TTY environment). A small `components/ui/` folder (`Button`, `Input`, `Card`, `Badge`, `InitialsAvatar`, `LoadingScreen`, `Chip`) holds the project's own thin wrappers per CLAUDE.md's "component-first" rule — every screen routes through these instead of re-inventing button/input/badge styling. `features/<domain>/` stayed the existing layout rather than renaming to the convention's illustrative `screens/` — an explicit, asked-for decision to avoid a large, purely-mechanical import-path rename.

Two composite widgets stayed intentionally custom rather than forced into a gluestack primitive: `LiveTrackingMap` (wraps `react-native-maps`, not a concern gluestack covers) and `StatusTimeline` (a bespoke stepper gluestack has no equivalent for) — both are the documented "custom primitive only when the library doesn't cover it" exception.

**Setup note for whoever runs this next**: `apps/mobile`'s `react@19.1.0` conflicts with `apps/web`'s newer `react-dom` peer requirement under npm workspace hoisting (the same root cause as the pre-existing `next build`/`next lint` issue) — `@gluestack-ui/themed`'s install needed `npm install --legacy-peer-deps` at the repo root rather than a plain `expo install`. Not a gluestack-specific problem; the same conflict will resurface for any new `apps/mobile` dependency with peer-dependency metadata until the underlying React-version split is resolved (tracked in the existing Reconciliation Notes row).

**Not fully done**: no dark-mode theming (gluestack's config supports it; MOTIQ hasn't opted in). No custom brand theme override — using gluestack's stock default palette/tokens rather than a MOTIQ-specific design language. Toast/Modal/Select/Tabs/Dialog primitives from CLAUDE.md's example list were not adopted anywhere, since no current screen has a use for them — not a gap, just unexercised.

## Phase 13 — Visual Design Pass: Brand Theme & Iconography (complete)

Phase 12's retrofit made every screen route through gluestack-ui, but still used gluestack's stock default blue palette and emoji as icons (tab bar, map pins, star ratings, back arrows) — functional but generic. This phase gives the app an actual visual identity: a custom brand theme (`theme/gluestackConfig.ts`, MOTIQ indigo `#4F46E5` layered onto gluestack's token set via the officially-supported `tokens.colors` override) and `lucide-react-native` for every icon that was previously an emoji or bare text glyph — tab bar icons, issue-type chips (`theme/issueIcons.ts`, Ch2's breakdown taxonomy each get a real icon: truck, wrench, fuel, tire, battery), map pins and the recenter button, star ratings, back/logout/upload/save affordances, and a `StatusTimeline` checkmark for completed steps.

New shared primitives: `EmptyState` (icon + title + description, replacing bare gray "no X yet" text across History/Jobs/KYC) and `Card`'s own default shadow (screens no longer each remember to add one). `Button` gained an optional leading-icon slot.

**A real bug found and fixed along the way**: `Button`'s `outline` variant was mapped to gluestack's `action="secondary"`, which resolves to a flat gray outline with no relation to the brand palette — every "outline" button in the app (Welcome's provider CTA, Rate/Profile screens, JobOffer's decline button) was rendering off-brand gray instead of indigo. Remapped to `action="primary"` (verified against gluestack's own `Button.js` theme source, which sets `_text`/`_icon` color to `$primary600` for that combination but leaves `secondary`+`outline` at a generic gray) — now every outline button matches the brand consistently.

**Verified** the same way as Phase 12: `npx expo export --platform android` compiles clean (4166 modules, up from 2380 — mostly `lucide-react-native`'s icon set pulled in), plus `tsc --noEmit` and `eslint` both clean.

**Not fully done**: no dark-mode palette tuning (the brand override only touches the `primary` scale; gluestack's dark-mode tokens still fall back to stock). No custom font — using the system font stack gluestack ships with. Document-type chips in `KycUploadScreen` didn't get per-type icons (only issue-type chips did) — deliberately scoped out to keep this pass bounded rather than re-touching every remaining screen.

**Post-install bugs found and fixed once real device testing resumed** (not caught by `tsc`/`eslint`, which don't execute a Metro bundle):
- `react-refresh` (a real `expo` dependency `babel-preset-expo` needs) silently went missing from `node_modules` during the `--legacy-peer-deps` install above — pinned explicitly in `apps/mobile/package.json`'s devDependencies as a real fix, not a workaround.
- `@gluestack-ui/themed` → `@gluestack-ui/overlay` → `@react-native-aria/interactions` → `@react-aria/utils`'s animation helper (`node_modules/react-aria/dist/private/utils/animation.cjs`) unconditionally `require("react-dom")` at module load — a genuine react-aria/React-Native interop bug (an old `@react-native-aria/interactions@0.2.16`, pinned to `@react-aria/utils@^3.6.0`, resolved against a much newer `3.34.1` that added this import). The code path that calls `react-dom`'s `flushSync` only ever runs against a real DOM node (`'getAnimations' in ref.current`) — never true for a React Native ref, so it's genuinely dead code on this platform, not a silently-broken feature. Fixed with a Metro resolver alias (`apps/mobile/metro.config.js`'s `resolver.extraNodeModules`) pointing `react-dom` at a small local shim (`apps/mobile/shims/react-dom.js`) instead of installing the real, DOM-dependent package. Verified with `npx expo export --platform android`, which forces a full non-interactive bundle build exercising the exact same resolver — confirmed compiling clean (2380 modules) after the fix, where it previously failed with `Unable to resolve "react-dom"`.
